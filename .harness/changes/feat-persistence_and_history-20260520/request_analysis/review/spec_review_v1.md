## 1. 需求完整性检查

| 检查项 | 状态 | 说明 |
|--------|------|------|
| `sessions` 表一致性 | ✅ | 保持现状，不做改动 |

| `browser_states` 表重构设计 | ✅ | 将 `session_id` 主键修改为独立主键 `id`，以便支持同一个会话多条历史截图 |

### 1.3 澄清问题处理

| 问题 | 决策 |
|------|------|
| 会话切换时后台运行的 Agent 怎么处理？ | 后端保持并发异步运行，切换时继续执行；再次切换回来时直接重载新状态。 |
| 截图在 SQLite 中的存储体积优化？ | 采纳单用户 SQLite 存储 Base64 PNG 方案，在会话删除时增加完整的联级物理删除以避免膨胀。 |

## 3. 技术方案可行性检查

### 3.1 架构设计与兼容性

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 数据库 schema 迁移方案 | ✅ | 在 `init_db()` 中动态判断 `browser_states` 是否具有主键/无 `id` 列，采取安全 DROP 并重新 CREATE，非常适合当前开发阶段。 |
| 消息与截图持久化时机 | ✅ | 用户提问在 HTTP 层 `/api/agui` 即时保存；Agent 助手消息和步骤截图在 `on_step_end` 钩子中异步持久化，逻辑非常自然。 |
| 前端 CopilotKit v2 兼容性 | ✅ | CopilotKit 的 `agent` 暴露了 `setMessages` 接口，可以在 `sessionId` 更改时将历史消息灌入，绕过原有的复杂交互，实现瞬间重载。 |
| 前端历史与 Live 状态合并 | ✅ | 使用 sessionId 判断，将 api 抓取的 history 与 `useStateSnapshot` 发送的实时事件根据步骤正序合并去重，保证平滑切换。 |

## 4. 风险识别

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| 旧数据迁移冲突 | 低 | 数据库初始化加入自适应升级判断，若表结构不匹配则清理并重建（开发期无重要用户数据）。 |
| Base64 大数据量存储导致性能下降 | 中 | SQLite 在 GB 级别下检索极快，且建立了相应的索引和级联删除机制，在删除会话时强制清理。 |
| 切换会话时渲染闪烁或状态错位 | 低 | 前端在切换 sessionId 时，先清空本地 states，再异步加载，防止前一会话状态残留。 |
