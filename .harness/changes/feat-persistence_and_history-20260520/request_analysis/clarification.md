# 需求澄清问题与设计决议

为了保证本次数据持久化和历史会话展示功能的最佳开发效果，我们在此对设计细节与技术选型进行梳理和决议。

---

## 🙋‍♂️ 澄清问题

### 问题 1: 当用户在前端切换会话时，如果前一个会话的 Agent 仍在后台运行，该如何处理？
* **背景**:
  FastAPI 后端在 `AgentService` 中为每个 `session_id` 独立维护着各自的 Agent 实例。当用户点击侧边栏切换至新会话时，旧会话的运行任务仍在执行。
* **推荐解决方案 (已采纳)**:
  前端切换会话时，后端的旧 Agent 继续异步运行直至结束或遇到暂停，因为每个会话在后端都是线程隔离（基于 session_id）的。前端再次切回原会话时，可以直接重载最新的消息历史和截图，与后台进度无缝对齐。
* **决议**: 采纳推荐方案。后端不作强制停止限制，保障多会话的并发流式运行体验。

---

### 问题 2: `browser_states` 数据库截图文件的存储形式与性能考量？
* **背景**:
  浏览器截图在 `browser-use` 中使用的是 Base64 编码的 PNG 字符串。将其完整写入 SQLite 数据库虽然简单方便，但频繁写入可能会使 SQLite 文件的体积在长会话下快速膨胀。
* **推荐解决方案 (已采纳)**:
  由于该项目是一个单用户的 AI 个人工作台，SQLite 的数据并发与体积承载力（支持高达数TB）在本地运行时完全不用担心。同时，在 `delete_session` 的清理中必须级联执行对 `browser_states` 和 `messages` 中大图/长文本历史数据的完全物理删除，以保持数据库的小巧和干净。
* **决议**: 采纳推荐方案，使用 SQLite 存储，并在会话删除时增加完整的联级删除。
