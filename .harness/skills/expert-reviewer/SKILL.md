# 专家评审

## 评审理念

**专家评审是确保项目方向正确、降低后期返工成本的关键环节。** 专家评审不仅是检查文档字面意思，更侧重于从专业视角识别潜在风险与逻辑漏洞。通过这些维度的评审，专家能够帮助团队在代码编写之前发现并解决 70%~80% 的潜在问题。

## 评审维度

### 1. 业务与功能逻辑的完备性
- 核心业务流程是否闭环
- 异常流程（断网、非法输入、越权操作）是否有明确定义
- 功能描述是否存在歧义
- 开发、测试、业务三方对功能理解是否一致

### 2. 技术可行性与约束条件
| 评估项 | 评审要点 |
|--------|----------|
| 架构适配性 | 是否与现有系统架构冲突，是否需要大规模重构 |
| 性能瓶颈 | 高并发/大数据量处理下，硬件或中间件是否支撑 |
| 第三方依赖 | 是否强依赖尚未交付的第三方接口或外部系统 |

### 3. 需求的一致性与逻辑严密性
- 新需求与现有系统功能是否存在冲突
- 新增权限逻辑是否破坏原有安全模型
- 新引入的数据字段是否与存量数据定义矛盾
- 图表（用例图、流程图）与文字说明是否逻辑自洽

### 4. 可测试性与可验证性
- 需求描述是否具体、可量化
- 每一个功能点是否能转化为具体测试用例
- 示例：不能只写"系统响应要快"，应定义为"在100并发用户下首页加载≤2秒"

### 5. 非功能性需求评审
| 类别 | 评审要点 |
|------|----------|
| 安全性 | 数据加密、身份认证、防SQL注入等安全标准 |
| 可靠性 | 故障恢复能力、在线率要求 |
| 易用性 | UI/UX是否符合目标用户习惯，操作路径是否过长 |
| 可维护性 | 代码扩展空间、日志监控完整性 |

### 6. 合规性与风险评估
- 法律合规、行业标准、数据隐私（如个人信息保护）
- 识别高风险部分，建议分阶段实施或技术预研

## 评审类型

| 类型 | 时机 | 内容 | 产出物 |
|------|------|------|--------|
| Plan Review | 阶段2 | spec.md + tasks.md | `*_review_v*.md` |
| Execution Review | 阶段4/6 | 代码/测试 | `*_review_v*.md` |

### Plan Review 检查项
1. **完整性**: 输入输出是否完整
2. **一致性**: tasks与spec是否匹配
3. **可执行性**: 任务是否可执行
4. **验收标准**: 是否清晰可验证

### Execution Review 检查项
1. **正确性**: 逻辑是否正确
2. **规范性**: 是否遵循编码规范
3. **安全性**: 是否有安全漏洞
4. **性能**: 是否有性能问题

## 评审意见格式

```markdown
## 评审意见

### MUST FIX
| 位置 | 问题 | 修改建议 |
|------|------|----------|

### LOW
| 位置 | 问题 | 修改建议 |
|------|------|----------|
```

## 优先级定义

| 优先级 | 含义 | 处理 |
|--------|------|------|
| MUST FIX | 阻塞问题 | 修复前不能进入下一阶段 |
| LOW | 建议改进 | 尽量修复 |
| INFO | 参考信息 | 可选 |

## 质量门禁

- MUST FIX 问题数 = 0
- 评审轮次 ≤ 限制（需求3轮，编码/测试2轮）

详细评审清单见 [references/review-checklist.md](references/review-checklist.md)

## 质量门禁脚本

阶段完成后，可使用脚本验证产出物：

```bash
python scripts/check_quality_gate.py <change-id> <stage>
```

**参数**:
- `<stage>`: request | coding | unit_test

**示例**:
```bash
# 验证需求评审产出
python scripts/check_quality_gate.py feat-ai-workspace-20260508 request
# 验证编码评审产出
python scripts/check_quality_gate.py feat-ai-workspace-20260508 coding
```
