# 开发流程规范

## 10 阶段开发流程

```
需求分析 → 需求评审 → 编码实现 → 编码评审 → 单元测试编写
    → 单元测试评审 → 代码推送 → CI验证 → 部署验证 → 用户确认
```

## 阶段详解

### 阶段 1: 需求分析
**Entry Criteria**: 用户需求描述
**Skill**: `request-analysis`
**产出物**:
- `.harness/changes/{change-id}/request_analysis/xmind.md` - 思维导图 (Mermaid 格式)
- `.harness/changes/{change-id}/request_analysis/spec.md` - 需求规格说明书
- `.harness/changes/{change-id}/request_analysis/tasks.md` - 任务拆解清单
- `.harness/changes/{change-id}/request_analysis/uml.md` - 架构图(可选)

**Quality Gate**:
- [xmind.md] 包含完整的业务需求思维导图，覆盖核心概念、功能模块、用户场景
- [xmind.md] 使用 Mermaid 格式，节点清晰、层级合理
- [uml.md] 业务逻辑表达完整(仅在`uml.md`文件存在时检查)
- [spec.md] 包含完整的输入输出定义
- [tasks.md] 包含可执行的子任务列表，每个子任务有明确的验收标准

### 阶段 2: 需求评审
**Entry Criteria**: spec.md + tasks.md
**Skill**: `expert-reviewer`
**产出物**:
- `.harness/changes/{change-id}/request_analysis/review/spec_review_v1.md`
- `.harness/changes/{change-id}/request_analysis/review/tasks_review_v1.md`

**Quality Gate**:
- 评审意见已处理
- 最多 3 轮评审
- Human-in-the-Loop 确认

**流转条件**:
- APPROVED → 进入阶段 3
- REVISION REQUIRED → 返回阶段 1

### 阶段 3: 编码实现
**Entry Criteria**: 评审通过的 spec
**Skill**: `coding-skill` + 8 份分层编码 Spec
**产出物**:
- 实现代码
- `.harness/changes/{change-id}/coding/coding_report_v1.md`

**Quality Gate**:
- 代码编译通过
- 遵循分层编码规范
- 无硬编码值

### 阶段 4: 编码评审
**Entry Criteria**: 实现代码
**Skill**: `expert-reviewer`
**产出物**:
- `.harness/changes/{change-id}/coding/review/code_review_v1.md`

**Quality Gate**:
- MUST FIX 问题已处理
- 最多 2 轮评审
- Human-in-the-Loop 确认

### 阶段 5: 单元测试编写
**Entry Criteria**: 评审通过的代码
**Skill**: `unit-test-write`
**产出物**:
- 测试用例
- `.harness/changes/{change-id}/unit_test/test_report_v1.md`

**Quality Gate**:
- 改动驱动的测试覆盖
- 优先使用真实请求数据构造测试

### 阶段 6: 单元测试评审
**Entry Criteria**: 测试用例
**Skill**: `expert-reviewer`
**产出物**:
- `.harness/changes/{change-id}/unit_test/review/test_review_v1.md`

**Quality Gate**:
- 评审意见已处理
- 最多 2 轮评审

### 阶段 7: 代码推送
**Entry Criteria**: 评审通过的代码+测试
**Skill**: `code-review`
**产出物**:
- Git 提交
- PR 创建

**Quality Gate**:
- 格式规范检查通过
- 无 console.log 语句
- 注释已清理

### 阶段 8: CI 验证
**Entry Criteria**: 推送的代码
**Skill**: `unit-test-ci`
**产出物**:
- `.harness/changes/{change-id}/ci_result/ci_result_v1.md`

**Quality Gate** (可程序化验证):
```
status == SUCCESS && total_tests > 0 && passed == total
```

**回退条件**:
- tests=0/0 → 返回阶段 5
- 编译错误 → 返回阶段 3

### 阶段 9: 部署验证
**Entry Criteria**: CI 通过的代码
**Skill**: `deploy-verify`
**产出物**:
- `.harness/changes/{change-id}/deployment/deploy_report_v1.md`

**Quality Gate**:
- 部署成功
- 基础功能验证通过

### 阶段 10: 用户确认
**Entry Criteria**: 部署验证通过
**Human-in-the-Loop 确认**

## 回退路径（Rollback Routes）

| 失败条件 | 回退阶段 | 处理方式 |
|----------|----------|----------|
| CI 失败 (tests=0/0) | 阶段 5 | 补充测试用例 |
| 编译错误 | 阶段 3 | 修复代码 |
| 需求不符 | 阶段 1 | 重新分析需求 |
| 评审不通过 | 上一评审阶段 | 修复问题 |

## 评审循环上限

- 需求评审：最多 3 轮
- 编码评审：最多 2 轮
- 测试评审：最多 2 轮
- 超出上限 → 升级到人工决策

## Human-in-the-Loop 确认点

1. 需求待决议确认（阶段 1 后）
2. 计划评审后确认（阶段 2 后）
3. 编码评审后确认（阶段 4 后）
4. 部署环境参数确认（阶段 9 前）
5. 最终交付确认（阶段 10）

## Git 提交规范

```
<type>: <描述>

<可选的详细说明>
```

### Type 类型
- `feat`: 新功能
- `fix`: 修复bug
- `refactor`: 重构
- `docs`: 文档
- `test`: 测试
- `chore`: 杂项
- `perf`: 性能优化
- `ci`: CI 配置

## Dry Run 验证

在拿真实需求使用 Harness 之前，应当用一个虚拟需求完整走一遍全流程，验证：
- CI 门禁正确检查测试用例数 > 0
- 评审报告在简单需求下正常生成
- 摘要文件无重复行
- 部署参数正确

## 核心原则

1. **流程一致性优先于流程效率**
2. **质量门禁必须可程序化验证**
3. **分离执行与评判是关键杠杆**
4. **规范是活文档，需要持续迭代**
